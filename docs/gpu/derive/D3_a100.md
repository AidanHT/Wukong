### 1.5 cuBLASLt IMMA int8 expectations

FACT (<https://docs.nvidia.com/cuda/cublas/index.html>, corroborated by <https://www.corsix.org/content/cublaslt-notes>):
to reach the **IMMA** (integer tensor-core) kernels with `computeType = CUDA_R_32I`, cuBLASLt requires
a specific opaque layout family:
- A, C, D: `CUDA_R_8I` / `CUBLAS_OP_N` / **`CUBLASLT_ORDER_COL32`**
- B: `CUDA_R_8I` / **`CUBLAS_OP_T`** / `CUBLASLT_ORDER_COL4_4R2_8C` (Turing **or Ampere**) or
  **`CUBLASLT_ORDER_COL32_2R_4R4`** (Ampere-preferred)
- The layouts are documented as "completely opaque"; NVIDIA's own guidance is to convert with
  `cublasLtMatrixTransform`, and "conversions obviously come with a time cost".
- "Performance can be further improved by using the COL32 / COL32_2R_4R4 / COL32 layout… however,
  while COL32 is the most performant layout, it comes with an associated cost of layout conversion
  which may cancel out any gains."

**Consequence for the peer bar.** Wukong's int8 kernel is plain row-major NT (`C = A·Bᵀ`, u8×i8→i32).
An honest A100 IMMA peer must either (a) pay the `cublasLtMatrixTransform` cost inside the timed
region — which is the fair comparison for a *user* holding row-major tensors — or (b) pre-transform
outside it and be labelled a **layout-privileged** peer. On the 4050 the existing
`int8_gemm_vs_peers` numbers (`BENCHMARKS.md:312`, "96–105% @2048³, beats IMMA") must be re-read
against whichever convention that harness used; if it pre-transformed, "beats IMMA" is inflated.
**Flagged as an audit item, not a claim — I did not verify the harness's transform placement.**

### 1.6 fp8 is architecturally absent on sm_80

Four independent sources, none of which can be read as "A100 has fp8":

1. **PTX ISA** (<https://docs.nvidia.com/cuda/parallel-thread-execution/>, feature-availability notes):
   `cvt` with `.e4m3x2` / `.e5m2x2` "requires PTX ISA version 8.1 or later" and target **sm_89 or
   higher**; support for these conversions was *extended to* sm_89 — i.e. it did not exist on sm_80.
   The `mma` fp8 variants carry the same target requirement.
2. **Ampere Tuning Guide** (cc 8.0, fetched in full): **zero occurrences of FP8**. Its precision list
   for the 3rd-gen tensor core is FP64 / TF32 / BF16 / FP16 / INT8 / INT4 / binary.
3. **Ada Tuning Guide** (cc 8.9): "…new Ada Fourth Generation Tensor Cores featuring the **Hopper FP8**
   Transformer Engine" — fp8 arrives *with* the 4th-gen core, one generation after A100's 3rd-gen.
4. **A100 datasheet spec table** (§1.1): no FP8 row exists; the lowest float precision listed is BF16/FP16.
5. **NVIDIA Transformer Engine**: "FP8 features require Compute Capability 8.9+"; on Ampere/A100 the
   library documents **BF16 as the fallback precision**.
   <https://github.com/NVIDIA/TransformerEngine>

**Documented fallbacks on A100: BF16 (312 TFLOPS, same peak as FP16 — training) and INT8 (624 TOPS,
2× the FP16 rate — inference).** Both are already shipped Wukong families
(`ptx_wmma.rs::PIPE_BF16`, `ptx_int8.rs`), so the capability decline has a real destination.

## 2. DERIVED — which 4050 verdicts flip, one by one

Method note: every occupancy figure below is `min(SMEM limit, register limit, block limit, warp limit)`
per SM. SMEM per stage for the int8 swz kernel is `(bm+bn)·BK` bytes (BK=64, 1 byte/element);
for the f16 mma kernel it is `stages·(bm+bn)·(bk+pad)·2` (the crate's own `CliffCfg::smem_bytes`,
`ptx_wmma.rs:303`).

### (a) "64×64 warp tile beats 256×128 CTA" at 108 SMs — **DOES NOT FLIP for the stated reason**

The shipped verdict (`ptx_int8.rs:919-926`): 128×128 CTA / 64×64 warp tile / 4 warps, "bigger CTA
tiles (256×128) instead *lose* on the 20-SM 4050 (**1 CTA/SM starves latency hiding**)".

First, a naming correction that matters: **CUTLASS's SM80 optimum has the same 64×64 warp tile Wukong
already ships** (§1.4 — every 128×128 [2,2,1] and 256×128 [4,2,1] entry is a 64×64 warp tile). The
warp tile is not the open question on A100; the **CTA tile and the stage count** are.

DERIVED occupancy for the 256×128 / 64×64-warp / 8-warp (256-thread) candidate:
- Accumulators/thread = 64·64/32 = **128** i32 registers, plus ~2 A-fragment b32 sets (4 regs each ×
  tm=4) + ~2 B-fragment b32 sets (2 regs × tn=8) + addressing ≈ **~180–190 regs/thread** (DERIVED
  estimate; the crate's own comment implies ≤170 for the 4-warp case).
- Register limit = 65536 / (256 threads × ~185) ≈ **1.38 → 1 CTA/SM**.
- **The register file is 64K/SM on BOTH cc 8.9 and cc 8.0 (FACT §1.3).** So the "1 CTA/SM" that killed
  256×128 on the 4050 is **architecture-invariant**. 108 SMs does not buy a second CTA.

**Verdict (a): the stated cause does not flip.** What *does* change is that the 4050 had no way to
compensate for 1 CTA/SM (its 48 KiB static / 99 KB dynamic SMEM could not fund a deep pipeline at a
384-row·64-K staging footprint), whereas A100's 163 KB can. CUTLASS's own SM80 answer is exactly this
trade: run **1–2 CTAs/SM with a 3–6-stage pipeline** instead of 3 CTAs/SM with a 2-stage one.
128×256×64 at 3 stages = (128+256)·64·3 = **72 KiB** — legal on A100 *and* on Ada, but only via the
dynamic-SMEM opt-in the crate has never used (`shared_mem_bytes: 0` everywhere, no
`cuFuncSetAttribute`, §2.3 of the plan). 128×256×**128** at 3 stages = **144 KiB** — legal on A100
(≤163 KB), **impossible on Ada** (>99 KB). That last shape is the genuinely A100-only configuration.

**And a second, opposite effect that the "bigger tiles at more SMs" intuition gets exactly backwards
— wave quantization at 108 SMs.** DERIVED CTA counts (`ceil(M/bm)·ceil(N/bn)`):

| square GEMM | 128×128 tiles | on 20 SMs @3 CTA/SM (60/wave) | on 108 SMs @3 CTA/SM (324/wave) | 256×128 tiles | on 108 SMs @1 CTA/SM (108/wave) |
|---|---|---|---|---|---|
| 1024³ | 64 | 1.07 waves | **0.20 wave — 44 of 108 SMs get NO work** | 32 | **0.30 wave — 76 SMs idle** |
| 2048³ | 256 | 4.27 | 0.79 (2.4 CTA/SM, 79% of capacity) | 128 | 1.19 (**16% tail waste**) |
| 4096³ | 1024 | 17.1 | 3.16 (5% tail) | 512 | 4.74 (5.5% tail) |
| 8192³ | 4096 | 68.3 | 12.6 | 2048 | 19.0 |

**The 4050 was never grid-starved at any GEMM ≥1024². The A100 is grid-starved below ~2048².**
Threshold to merely cover all 108 SMs with one 128×128 CTA each: `M·N ≥ 108·128·128 = 1.77 M`
(≈1330² square). To fill 3 CTAs/SM: `M·N ≥ 5.31 M` (≈2305²). With 256×128: 1 CTA/SM coverage needs
`M·N ≥ 3.54 M` (≈1881²).

**Therefore the first A100 int8/fp16 GEMM lever is not bigger tiles — it is split-K / stream-K and
*smaller* tiles at ≤2048², and the bigger-tile-plus-deep-pipeline argument applies only at ≥4096².**
This is the inverse of what the plan's "the literature expects the opposite verdict at 108+ SMs"
(§2.4) anticipates, and it is the single most surprising result in this dossier.

### (b) "3-stage pipeline MEASURED NEGATIVE" — **FLIPS, and the arithmetic is exact**

Shipped verdict (`ptx_int8.rs:937-950`): 3-stage 128×128 BK=64 int8 "loses at every size (1024³ ~67%,
2048³ ~69–80%, 4096³ ~65% of cuBLAS, vs the 2-stage's ~84/100/72%)", diagnosed as "deepening to 48 KiB
SMEM only *cuts occupancy* (fewer CTAs/SM) with no compute-bound payoff".

**That diagnosis is correct and it is 100% an SMEM-capacity artifact.** SMEM per stage for
128×128/BK=64 int8 = (128+128)·64 = **16 KiB**. DERIVED:

| stages | SMEM/CTA | CTAs/SM on **4050** (100 KB) | CTAs/SM on **A100** (164 KB) | register limit (both) |
|---|---|---|---|---|
| 2 (shipped) | 32 KiB | ⌊100/32⌋ = **3** | ⌊164/32⌋ = 5 | ~3 ← binds |
| **3 (CUTLASS floor)** | 48 KiB | ⌊100/48⌋ = **2 ← SMEM binds, −33% occupancy** | ⌊164/48⌋ = **3 ← SMEM does NOT bind** | ~3 ← binds |
| 4 | 64 KiB | 1 | 2 | ~3 |
| 5 | 80 KiB | 1 | 2 | ~3 |
| 6 | 96 KiB | 1 | 1 | ~3 |

On the 4050, going s2→s3 costs a third of the occupancy. **On A100 it costs nothing** — the register
file still binds at ~3 CTAs/SM, exactly where s2 already was. The deeper prefetch window is free.

**Reconciliation with "CUTLASS's SM80 floor is 3 stages":** there is no contradiction to reconcile.
CUTLASS's floor of 3 is an *SM80* statement (every entry in §1.4's list is min_cc=80, stages ≥ 3), and
3 stages at the crate's tile is *precisely the depth A100's 164 KB makes occupancy-free and Ada's
100 KB does not*. Wukong's 2-stage production config is not a disagreement with CUTLASS — it is the
correct Ada answer to a constraint CUTLASS's SM80 tables never faced. The same reasoning applies to
the f16 side: `cliff_swz_s3` is 3·(128+128)·32·2 = **48 KiB exactly** (the crate says so at
`ptx_wmma.rs:329-332`, "s3 no-pad = 48 KiB exactly"), which on the 4050 means ⌊100/48⌋=2 CTAs/SM, on
A100 ⌊164/48⌋=3. And `cliff_swz_s3` **padded** (60 KiB) — rejected on Ada as ">the 48 KiB static cap"
— is legal on A100 with the dynamic opt-in at ⌊164/60⌋=2 CTAs/SM.

**Note the trap:** the 48 KB *static* limit is **identical on both parts** (FACT §1.3 — "static shared
memory allocations remain limited to 48 KB" on cc 8.0 too). Retargeting the header to `sm_80` alone
buys **zero** extra SMEM. The 164 KB is reachable *only* through dynamic SMEM +
`cuFuncSetAttribute(CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES, …)`, which the crate has nowhere
(plan §2.3). **Phase 2's dynamic-SMEM work is a hard prerequisite for verdict (b) to be testable at
all** — without it, an A100 run reproduces the 4050's s3 loss for the *same* reason and would
falsely "confirm" the negative verdict.

### (c) Norm-kernel grid underfill — **the threshold moves 7.2×, and the design has a 50% ceiling**

FACT (repo): `ptx_norm.rs:32-33` — "one warp per row (block_dim=32, grid=rows)"; confirmed at the
launch sites, e.g. `gpu.rs:2958` `LaunchConfig { grid_dim: (s,1,1), block_dim: (32,1,1) }` and
`gpu.rs:3430`/`:3515` in the resident layer.

DERIVED — a 32-thread CTA is 1 warp, so the block-count cap, not the warp cap, binds:

| | 4050 (24 blocks/SM, 48 warps/SM) | A100 (32 blocks/SM, 64 warps/SM) |
|---|---|---|
| rows to touch every SM | **20** | **108** |
| rows to saturate the block-slot cap | 20·24 = **480** | 108·32 = **3456** |
| peak achievable warp occupancy | 24/48 = **50%** | 32/64 = **50%** |

So: the **relative** ceiling is a coincidental tie at 50% — the one-warp-per-CTA design can never
exceed half the warp slots on either part — but the **absolute saturation threshold rises 7.2×**
(480 → 3456 rows), while the memory system got 8.1–10.6× faster. Concretely, with GPT-2-124M-shaped
LayerNorm (`cols=768`, f32):

| rows (= B·S) | 4050 block-slot fill | A100 block-slot fill | A100 CTAs/SM |
|---|---|---|---|
| 1 (decode, B=1) | 4% of one SM | **1 SM of 108 busy = 0.9% of the machine** | 0.009 |
| 128 | 27% | 3.7% | 1.2 |
| 512 | **107% — saturated** | 15% | 4.7 |
| 1024 (S=1024, B=1) | 213% — saturated | **30%** | 9.5 |
| 3456 | saturated | **100%** | 32 |
| 12288 (softmax, B·H·S = 1·12·1024) | saturated | saturated | 32 |

**Verdict (c): flips hard.** A shape (1024 rows) that saturated the 4050 leaves A100 at 30% of its
block slots and 15% of its warp slots. And a second, larger effect stacks on top: at 2039 GB/s a
1024×768 f32 LayerNorm moves 6.3 MB → **3.1 µs ideal**, which is the same order as a single kernel
launch on Linux (~2–5 µs). **The kernel stops being bandwidth-bound and becomes launch-bound.** On
the 4050 the same op is ~33 µs ideal and comfortably bandwidth-bound.

The two structural fixes are device-independent and can be written before renting anything:
(i) multi-warp CTAs with an SMEM/`redux.sync` reduction (or a persistent grid-stride over rows) so
the grid is a function of `sm_count()` rather than `rows`; (ii) vectorized `ld.global.v4.f32` — at
cols=768 that is 6 `float4` per lane instead of 24 scalar loads.

### (d) The flash long-S "structural on 20 SMs" loss — **the premise is wrong, and the loss should get WORSE**

FACT (repo): `BENCHMARKS.md:~2131` — "the residual long-S loss is **structural (SFU/serial-softmax on
20 SMs)**, with no locally-measurable FA2 denominator to chase"; trails cuDNN at S ≥ 2048.
FACT (repo): the tensor-core flash launch is grid `(S/16, heads, 1)` with **one warp per CTA**
(`gpu.rs:2166-2180` `wmma_flash_plan`; `gpu.rs:2185` "grid `S/16`, one warp/CTA, static SMEM").

DERIVED, at D=64, single head:

| S | CTAs (=warps) launched | 4050: % of 480 block slots | A100: % of 3456 block slots | A100 CTAs/SM |
|---|---|---|---|---|
| 512 | 32 | 6.7% | 0.9% | 0.30 |
| 1024 | 64 | 13% | 1.9% | 0.59 |
| 2048 | 128 | 27% | 3.7% | 1.19 |
| **4096** | **256** | **53%** | **7.4%** | **2.4** |
| 4096, H=12 | 3072 | saturated (6.4×) | 89% | 28.4 |

**The long-S loss is not caused by having only 20 SMs — at S=4096 the 4050 was more than half full
and the A100 is 7.4% full.** The framing has cause and effect backwards: 108 SMs makes the *same*
grid-shape problem **5.4× worse**, not better.

A second, independent effect points the same way. SFU throughput is **16 results/clk/SM on both**
parts (FACT: A100 GA100 = 4 SFU per processing block × 4 = 16/SM; Ada AD10x is likewise 4/partition).
DERIVED aggregate `ex2.approx` rate: A100 = 108 · 16 · 1.41 GHz ≈ **2.44 T/s**; 4050 ≈ 20 · 16 ·
2.37 GHz ≈ **0.76 T/s** → only **3.2×**. Meanwhile FP16 tensor throughput rose **~6.4×** (§1.3).
**The softmax-exp : MMA ratio therefore gets ~2× worse on A100.** A kernel that serialises exp against
MMA loses relatively more, not less.

**Verdict (d): re-diagnose, and expect the deficit to deepen.** The real levers are (i)
**flash-decoding / split-KV** so the grid is `(S/16, H, kv_splits)` and fills 108 SMs — this is
precisely why FA2 added it; (ii) multi-warp CTAs; (iii) overlapping `ex2.approx` with `mma` (the
warp-specialised `flash_*_ws` variants already built and gated at S≥4096, `ptx_flash.rs:56-58`, are
the right family — they should win by *more* on A100 than the 4–6% measured on the 4050). All three
are writable with no rented GPU.
**Conversely** the small-S occupancy *wins* (the plan's §2.7 worry) almost certainly invert: at S=512,
H=1 the A100 runs 32 one-warp CTAs on 108 SMs — 0.9% of the machine.

### (e) Bandwidth-bound families at 8–10× the memory bandwidth — three structural changes, not a scale factor

FACT (repo, `BENCHMARKS.md:2035-2044`): the peak denominator is the device's own queried
`2 × clock × busBytes` = **192.0 GB/s** on the 4050; the saxpy triad reached **183.9 GB/s = 95.7%**;
the 1:1 read/write mix 168.8 GB/s = 87.9%.
FACT (repo, `ptx.rs::SAXPY`): the kernel is **scalar** — one element per thread,
`ld.global.f32` ×2 + `st.global.f32`, **no vectorization, no grid-stride**; launched with cudarc's
`LaunchConfig::for_num_elems(n)`.
FACT (repo, `ptx_optim.rs:205-218`): the one correctly-scaling pattern, `grid_stride_cfg`, is
256-thread blocks × `32·sm_count()` — and `Gpu::sm_count()` (`gpu.rs:109`) **falls back to 20** if the
attribute query fails.

What changes **linearly** (uninteresting): the absolute GB/s of any already-saturating kernel.
What changes **structurally**:

1. **Launch overhead becomes the denominator at small N.** DERIVED time to move `3·N·4` bytes at
   2039 GB/s vs 192 GB/s:

   | N (f32) | bytes moved | 4050 ideal | A100-80SXM ideal | A100-40 (1555) ideal |
   |---|---|---|---|---|
   | 2²⁰ (1 M) | 12.6 MB | **65 µs** | **6.2 µs** | 8.1 µs |
   | 2²² | 50.3 MB | 262 µs | 24.7 µs | 32 µs |
   | 2²⁴ | 201 MB | 1.05 ms | 98.7 µs | 129 µs |

   A Linux kernel launch is ~2–5 µs. At N=2²⁰ that is **up to 45% of the A100's ideal time and 5% of
   the 4050's**. Every bandwidth number below ~2²² on A100 is contaminated unless graph-captured or
   amortised over many iterations. This also moves the `--backend=gpu` recognizer-offload break-even
   the **wrong** way: device compute got 8–10× faster while host↔device PCIe did not (Gen4 x16 ≈
   25 GB/s), so the minimum N at which offloading a single elementwise op beats the CPU **rises**.
2. **Every "working set vs L2" threshold is wrong by 3.3× — and the naive fix over-corrects.** The
   crate already queries `l2_cache_size()` (`gpu.rs:117`, added specifically because "the cliff
   comments have carried both 24 MB and 12 MB"), which is the right mechanism. But A100's 40 MB is
   **two 20 MB partitions** (FACT §1.2): a rasterization band or NT-store heuristic sized to 40 MB
   will straddle the partition boundary and pay cross-partition traffic. **DERIVED: the correct
   effective capacity for L2-locality tuning on A100 is ~20 MB, not 40 MB** — i.e. 1.67× the 4050's
   12 MB, not 3.33×. The f16 GEMM regime dispatcher (`gemm_nt_f16`, whose arms are described in terms
   of 16 MB / 48 MB working sets, `ptx_wmma.rs:228-247`) must be re-derived against that.
3. **Scalar-access memory-level parallelism gets tight.** Little's law: bytes-in-flight needed =
   BW × latency. Ampere global-load latency ≈ 290 ns at 1.41 GHz (~410 cycles). DERIVED: A100 needs
   ≈ **591 KB in flight** (5.5 KB/SM) vs the 4050's ≈ **56 KB** (2.8 KB/SM). With `for_num_elems`'s
   1024-thread blocks, A100 holds 2048 threads/SM × 8 B of outstanding loads ≈ 16 KB/SM — still
   sufficient, but with ~3× less headroom than the 4050 had, and *only* while occupancy is full.
   Switching saxpy/velem to `ld.global.v4` (16 B/thread) restores a 4× margin and is the cheap fix.

## 3. The fp8 story and what the capability gate must say

**Confirmed absent** (§1.6, five sources). The precise ISA statement is worth writing into the gate's
own comment, because it is not "Ampere has no fp8 tensor cores" but two separate PTX facts:
- `cvt.rn.satfinite.e4m3x2.f32` / `.e5m2x2.f32` require **PTX ISA ≥ 8.1 and target ≥ sm_89**.
- the `mma.sync` `.e4m3` / `.e5m2` variants carry the same **sm_89** floor.

So both halves of Wukong's fp8 family are affected: `ptx_fp8.rs` (E4M3 forward) **and**
`ptx_fp8_train.rs` (E5M2 backward + amax + delayed scaling), including their **host-side encoders'
byte-for-byte gates against the hardware converter** — there is no hardware converter on sm_80 to gate
against, so those tests must skip too, not merely the kernels.

**Documented fallbacks: BF16 (312 TFLOPS on A100 — identical peak to FP16) for training, INT8
(624 TOPS — 2× FP16) for inference.** NVIDIA's own Transformer Engine does exactly this on Ampere.

### What the gate must say (design constraints, not code)

1. **Predicate on compute capability, not on a device-name string or an arch enum.**
   `cc = (CU_DEVICE_ATTRIBUTE_COMPUTE_CAPABILITY_MAJOR, …_MINOR)`; the fp8 predicate is
   **`cc >= (8,9)`**. This is correct for sm_89 (8.9 ✓), sm_90 (9.0 ✓), sm_100/103 (10.x ✓),
   sm_120 (12.0 ✓) and sm_80 (8.0 ✗) with plain tuple ordering. Do **not** write `major >= 9` (kills
   Ada) or `cc >= (8,0)` (admits A100).
2. **It is a CAPABILITY decline, a third category distinct from the two the crate already has.**
   Today `WUKONG_GPU_REQUIRED=1` escalates *device-absence* skips into failures (`gpu.rs:4867-4880`,
   `diff::skip_or_fail`). A capability skip must **stay a skip under `WUKONG_GPU_REQUIRED=1`** — the
   device is present and healthy; the ISA simply lacks the instruction — while still printing loudly
   and being **counted**, so "12 fp8 tests skipped by capability on sm_80" is an asserted, reviewable
   number rather than silence. Reusing the device-absence path would turn a correct A100 run red;
   reusing a bare `return` would report `ok` having executed nothing (crate Hard Rule 3).
3. **It must name four things in the message**: the device's actual `sm_XX`, the required `sm_89`,
   the specific unsupported construct (`mma.*.e4m3` / `cvt.*.e4m3x2`), and the fallback family that
   *does* run here (bf16 / int8). A user reading the log should not have to consult a table.
4. **It must fire before PTX generation, not at `cuModuleLoadData`.** A driver JIT failure on fp8 PTX
   surfaces as a generic `CUDA_ERROR_INVALID_PTX`, and — per crate LANDMINE 6 — a failed load can
   leave the context sticky-errored so every *later* call fails identically, which reads as a cascade
   with the wrong root cause.
5. **Never silently substitute bf16 for fp8.** The plan's §3 consequence 1 says it: "gated off with a
   loud capability skip (never a silent fallback)". Note that NVIDIA's Transformer Engine *does*
   silently fall back on Ada — we explicitly should not; a silent fallback would make an fp8 benchmark
   number a bf16 number.
6. **The same mechanism generalises, so build it once**: `sm_90` gates wgmma/TMA (Phase 4), `sm_90`+
   gates `setmaxnreg`, and the **dynamic-SMEM ceiling itself is a capability** (99 KB on cc 8.9 vs
   163 KB on cc 8.0 vs 227 KB on cc 9.0) that the tile chooser must query rather than assume.
7. **Adjacent, cheap, do it in the same commit**: `ptx_fp8_train.rs` has **no ASCII gate** (plan §2.5,
   a crate-rule violation) — the fp8 family is being touched anyway.

## 4. PREDICTIONS — the 6-point confirmation grid for Phase 3b (1–2 h, Modal A100-40GB, ~$2.50/hr)

Ordered so the three correctness points run first and gate the three physics points. Every point
states its falsifier. Peak-bandwidth denominator on Modal's A100-40GB = **1555 GB/s** (FACT §1.1) —
use the device's own queried value, not this number.

**Hard prerequisite:** points 4 and 5 are meaningless unless Phase 2's **dynamic SMEM +
`cuFuncSetAttribute`** has landed. Without it the 48 KB *static* cap is identical on both parts
(FACT §1.3) and A100 will faithfully reproduce the 4050's s3 loss for the same reason — a false
confirmation of the negative verdict. If Phase 2 is incomplete, run points 1–3 + 6 only.

### Correctness

**P1 — Emission and load toward an older ISA.**
PREDICTION: with the Phase-2 header parameterization, **100% of non-fp8 PTX families emit
`.target sm_80` and load via `cuModuleLoadData` with zero errors**. Wukong's inventory is sm_80-legal
by construction: `mma.sync.m16n8k16` f16/bf16 (sm_80), `mma.sync.m16n8k32` u8/s8 (sm_80), `ldmatrix`
(sm_75), `cp.async` (sm_80 — the architecture that introduced it), `lop3` (sm_50), `shfl.sync`
(sm_30), `redux.sync` (sm_80). `.version 7.8` needs a CUDA-11.8-or-newer driver; Modal's r580/CUDA-13
hosts (plan §2.6) satisfy it.
FALSIFIER: any `CUDA_ERROR_INVALID_PTX` / `CUDA_ERROR_NO_BINARY_FOR_GPU` on a non-fp8 module. Most
likely culprits if it fires: a family whose header was missed by the parameterization (the census
counted **67** hardcoded `sm_89` sites), or `.minnctapersm` launch bounds interacting with the
different occupancy limits.
INFORMATION VALUE: this is the entire stated purpose of Phase 3b. It is the one direction
sm_89→sm_90 never tests.

**P2 — fp8 skips loudly, by capability, and nothing else does.**
PREDICTION: with `WUKONG_GPU_REQUIRED=1`, **exactly the fp8 tests skip** (count them from the source
*before* renting — `ptx_fp8*`, the E5M2 host-vs-device byte gate, the fp8 GEMM device gates, the
fp8 autotune candidates — so the run asserts a number, not a vibe), **zero fp8 tests pass**, and the
suite's exit status is **0**.
FALSIFIER (three distinct failure modes, all serious): (a) an fp8 test **passes** → it silently fell
back to bf16/int8, and every published fp8 number is suspect; (b) an fp8 test **fails the suite** →
the capability skip was wired into the device-absence path and a correct A100 run reports red; (c) an
fp8 test skips **silently** (libtest prints `ok` with captured stderr) → crate Hard Rule 3 violated.
(d) a *non*-fp8 test skips → an over-broad predicate (e.g. `major >= 9`) is disabling working families.

**P3 — Full suite green, and the integer gates bit-exact.**
Run: `WUKONG_GPU_REQUIRED=1 WUKONG_PEER_REQUIRED=1 cargo test -p wukong_codegen_gpu --features gpu`,
plus `lower::tests::run_corpus_matches_interp_oracle` and `megakernel::tests::mega_corpus_matches_oracle`
(both sweep `tests/run/*.wk` at -O0 and -O3), plus the 5 driver e2e tests.
PREDICTION: **0 failures.** Specifically, the **int8 gates pass bit-exactly (`==`)** — `mma` u8×i8→i32
is exact mod 2³² and architecture-invariant, so a *single* mismatched integer element is proof of a
real retarget bug, not a tolerance question. Float gates pass within the existing `c·√K·ε` bounds with
**no widening**; f32-accumulated `mma.m16n8k16` has an architecturally defined accumulation order, so
f16/bf16 GEMM should land at or very near 4050 error levels.
FALSIFIER: a tolerance failure that passes on sm_89. Most plausible legitimate cause: `ex2.approx` /
`rcp.approx` / `sqrt.approx` SFU ULP differences between Ada and Ampere in the norm and flash kernels
— which would be a genuine finding worth recording, and is precisely why the gates are tolerance-based
against an **independent f64 reference** rather than a recorded sm_89 output.

### Physics (highest information per rented minute)

**P4 — the 3-stage int8 flip.** Same-run adjacent A/B (`quant_int8_w64_s3_sweep`), ≥3 passes,
best-of-N minima, `int8_gemm_nt_w64_swz` (s2, 32 KiB) vs `_s3` (48 KiB) at 1024³ / 2048³ / 4096³.
PREDICTION: **s3/s2 ≥ 1.00 at every size on A100**, vs the 4050's measured `~67/84`, `~69–80/100`,
`~65/72` = **0.80 / 0.69–0.80 / 0.90**. Numeric bracket: **s3/s2 ∈ [1.00, 1.25]** on A100, largest at
4096³ (most HBM-latency-bound, most to gain from a deeper prefetch window). Mechanism (DERIVED §2b):
occupancy goes 3→2 CTAs/SM on the 4050 and **stays at 3** on A100.
FALSIFIER: s3 still loses at ≥2 of 3 sizes → the occupancy model is wrong and the 2-stage BK=64
latency-hiding argument ("int8 runs `mma` at 2× the fp16 rate") is the real cause, independent of
SMEM. That would be a *more* valuable finding than confirmation, because it kills the deep-pipeline
lever for int8 on every target and redirects Phase 3's H100 tuning budget.
CHEAP EXTENSION (same module cache, ~2 min): add s4 (64 KiB, 2 CTAs/SM) and s5 (80 KiB, 2 CTAs/SM) —
PREDICTION: s4/s5 lose to s3, because the occupancy drop resumes there. This localises the optimum
rather than just confirming a direction.

**P5 — CTA tile vs wave quantization at 108 SMs (the counter-intuitive one).**
Sweep `int8_gemm_swz_tile_ptx` (already generates arbitrary `(bm,bn,wm,wn,raster)`) over
**(128,128,2,2)** [shipped], **(256,128,4,2)** and **(128,256,2,4)** [CUTLASS's SM80 warp grids], at
1024³ and 4096³, each at s2 and (if dynamic SMEM landed) s3.
PREDICTION at **1024³**: the shipped 128×128 wins by **≥1.3×** over both 256-wide tiles. DERIVED
mechanism: 64 CTAs vs 32 CTAs on 108 SMs — the big tile leaves **76 of 108 SMs with no work at all**.
PREDICTION at **4096³**: at s2 the three are within **±10%** (1024 / 512 / 512 CTAs, all ≥4.7 waves,
tail waste ~5%); 256×128 pulls ahead **only** at s3+ with dynamic SMEM (72 KiB), and by **≤15%**.
PREDICTION overall: **the plan's stated expectation — "the literature expects the opposite verdict at
108+ SMs" (§2.4) — is falsified as written.** The register file is unchanged at 64K/SM (FACT §1.3), so
256×128 is 1 CTA/SM on A100 exactly as on the 4050; only pipeline depth, not SM count, can rescue it.
FALSIFIER: 256×128 wins at 1024³ → wave quantization is not the binding constraint at that size and
the CTA-count model is wrong.
SECOND-ORDER (record it, don't chase it): re-sweep `raster` ∈ {0, 8, 16, 32} against **20 MB**
(one L2 partition, §2e) rather than 40 MB. PREDICTION: the optimal band is **wider** than the 4050's
r8–r16 but **narrower than a naive 40 MB scaling would suggest**.

**P6 — fill-limited families: norm grid, flash grid, saxpy roofline.** One combined ~15-minute block.
- **Norm/softmax underfill.** LayerNorm at `cols=768`, `rows ∈ {1, 108, 512, 1024, 3456, 8192}`.
  PREDICTION: achieved GB/s is **~linear in rows up to rows ≈ 3456 and flat after**; quantitatively
  **GB/s(3456) / GB/s(512) ≥ 4×** on A100, vs **≤ 1.2×** on the 4050 (where 512 rows already exceeds
  the 480-slot cap). PREDICTION: at `rows=1024` (the shipped GPT-2 shape) A100 reaches **≤ 35% of the
  queried peak**. FALSIFIER: flat from rows=512 → the kernel is per-warp latency-bound (24 scalar
  strided loads per lane), not grid-bound, and the fix is `ld.global.v4` before multi-warp CTAs.
  Either outcome names the right fix; this is the highest information-per-second cell in the grid.
- **Flash grid fill.** Tensor-core flash, D=64, S=4096, H=1 vs H=12. PREDICTION: H=1 launches
  **256 one-warp CTAs = 2.4 CTAs/SM against a 32-CTA/SM ceiling (7.4% fill)**, and its
  per-SM throughput lands **well below** the 4050's at the same S; H=12 (3072 CTAs, 89% fill) recovers
  most of it. PREDICTION: the H=12/H=1 throughput ratio is **≥ 4×** on A100 vs the 4050's measured
  **2.0×** at S=2048. This directly falsifies "structural on 20 SMs" and points at flash-decoding /
  split-KV as the fix. FALSIFIER: H=1 and H=12 land within 1.5× → the kernel is per-warp bound, not
  fill-bound, and warp specialisation (already built) is the whole story.
- **Bandwidth roofline.** saxpy triad at `N ∈ {2²⁰, 2²², 2²⁴}` against the device's **own** queried
  `2 × clock × busBytes`. PREDICTION: **≥ 85% of peak at N = 2²⁴**, and **< 60% at N = 2²⁰** —
  purely launch/timer overhead, since the ideal time there is 8.1 µs (DERIVED §2e). The 4050 measured
  **95.7%** on a much smaller buffer, so a naive re-run at the old N would look like a regression and
  would not be one. PREDICTION: switching the generator to `ld.global.v4.f32` moves the N=2²² point up
  by **≥ 5 points**; on the 4050 it would be within noise.

## 5. Loose ends this dossier did NOT resolve (hand-offs)

1. **`gpu_accel.rs:118`** declines the fused-epilogue offload unless `M,N % 64 == 0 && K % 16 == 0` —
   literals mirroring the 64×64 tiling. If A100 dispatch moves to a 128×256 tile these become wrong in

2. **`Gpu::sm_count()` falls back to 20** (`gpu.rs:111`) if the attribute query fails. On a 108-SM part

3. **cuBLASLt IMMA peer fairness** (§1.5): whether the existing `int8_gemm_vs_peers` harness pays the

   any device.

   case). A free, device-less way to settle them: `ptxas -v --gpu-name sm_80` on the generated PTX
