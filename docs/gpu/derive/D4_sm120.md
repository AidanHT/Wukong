# D4 — Consumer Blackwell (`sm_120`) target dossier

Wave-0 research, $0, no device. Produced 2026-08-06 against `GPU_RETARGET_PLAN.md` §3 consequence 5
("`sm_120` (RTX PRO 6000) is added as a real-user target … the same ISA as an RTX 5090").

Every claim is labelled **FACT** (with source + confidence), **DERIVED** (reasoning from FACTs), or
**PREDICTION**. Where NVIDIA's own documents disagree, that is stated as **UNRESOLVED** rather than
papered over.

Doc versions read: CUDA Programming Guide **v13.3** (page last updated 2026-05-27), PTX ISA **9.3**,
Blackwell Tuning Guide (13.3), Blackwell Compatibility Guide (13.3, updated 2026-06-25), NVIDIA RTX
Blackwell GPU Architecture whitepaper **v1.1** (GeForce), NVIDIA RTX PRO Blackwell GPU Architecture
whitepaper **v1.1**.

---

## 0. Headline (read this if you read nothing else)

1. **Every PTX instruction Wukong emits today is `sm_89`-baseline-legal and therefore runs unmodified
   on `sm_120` by the PTX onion-layer model.** No `wgmma`, no `tcgen05`, no `mma.s4`, no arch-specific
   (`a`-suffix) feature anywhere in the tree. `sm_120` is the *cheapest* port in the whole ladder —
   cheaper than A100, which needs the fp8 family gated off.
2. **`sm_120`'s occupancy-relevant limits are byte-for-byte identical to Ada `sm_89`** (100 KB SMEM/SM,
   99 KB/block opt-in, 48 warps/SM, 24 blocks/SM, 64 K regs/SM, 128 KB unified L1/SMEM). The tile,
   stage and warp-tile *shapes* derived for the 4050 are exactly the feasible set on a 5090. Only the
   *counts* change (20 → 170/188 SMs, 12 → 96/128 MB L2, 192 → 1792 GB/s).
3. **The RTX PRO 6000 is NOT a performance proxy for the RTX 5090.** GeForce halves fp16/fp8 tensor
   throughput when the accumulator is FP32 — which is exactly what Wukong emits. The PRO card does
   not halve it. A `%-of-peak` number measured on RTX PRO 6000 must be halved before it predicts a
   5090. See §D4 — this is the single most important derived finding in this dossier.
4. **A dedicated `sm_120` codegen family is needed only to reach FP4/FP6/mxfp**, and that family is
   necessarily `sm_120a`/`sm_120f` — architecture/family-specific PTX that is *not* forward compatible
   and must be a separate module chosen by the runtime probe.

**FACT — the family/arch target system (PTX ISA 9.3 §11.1.2, CUDA PG v13.3 §5.1.2, HIGH).**
Three target flavours exist per SM: `sm_120` (baseline, onion-layer, forward compatible),
`sm_120f` (family-specific), `sm_120a` (architecture-specific, *not* forward compatible).
`Table 61 Architecture Families`: the **`sm_12x` family = `sm_120f`, `sm_121f`, future `sm_12x`**.
CUDA PG `Table 28`: `compute_120f` is compatible with compute capability **12.0 and 12.1** — i.e. an
`f`-target build covers RTX 5090 / RTX PRO 6000 *and* DGX Spark GB10.

**FACT — `wgmma` does NOT exist on `sm_120` (PTX ISA 9.3 §9.7.16, HIGH).** Every `wgmma` instruction —
`wgmma.mma_async`, `wgmma.mma_async.sp`, `wgmma.fence`, `wgmma.commit_group`, `wgmma.wait_group` —
carries the Target ISA Note **"Requires sm_90a."** `sm_90a` is architecture-specific, so it is not
merely absent from `sm_120`; it is unreachable from any other target. Verified verbatim, five
instructions. Answer to the plan's question: **NO, confirmed.**

**FACT — `tcgen05` / tensor memory does NOT exist on `sm_120` (PTX ISA 9.3 §9.7.17, HIGH).** Every
`tcgen05.*` instruction (`alloc`/`dealloc`, `ld`/`st`/`wait`, `cp`, `shift`, `mma`, `mma.sp`,
`mma.ws`, `mma.ws.sp`, `fence`, `commit`) carries **"Supported on following architectures: `sm_100a`
`sm_101a` (Renamed to `sm_110a` from PTX ISA version 9.0)"**, extended from PTX 8.8 to the `sm_10x`/
`sm_11x` *family* targets only. `sm_120a` appears in none of the tcgen05 lists. Answer: **NO,
confirmed.** Corollary: `setmaxnreg` (warp-specialisation register reallocation) is likewise
`sm_90a`/`sm_100a` only — the Hopper/Blackwell-DC producer-consumer idiom is **not** available on
consumer Blackwell.

**FACT — what `sm_120` DOES expose (PTX ISA 9.3 §9.7.15 + §11.1.2; CUDA PG v13.3 Table 33, HIGH).**

### 1.4 Toolchain floor and forward compatibility

**FACT — minimum PTX ISA / CUDA / driver to *name* `.target sm_120` (PTX ISA 9.3 §13.6 + the
version-support table, HIGH).**
*"PTX ISA version 8.7 introduces the following new features: **Adds support for `sm_120` target
architecture. Adds support for target `sm_120a`** …"*, and the support matrix reads
**PTX ISA 8.7 → CUDA 12.8, driver r570 → `sm_{120,120a}`**. (For contrast: PTX ISA 8.6 → CUDA 12.7,
r565 → `sm_{100,100a,101,101a}`.) So: **PTX `.version 8.7`, CUDA Toolkit 12.8, driver r570** is the
floor for `sm_120`. Wukong emits `.version 7.8` today (CUDA 11.8 era) — fine for the baseline
inventory, insufficient for anything `sm_120`-specific.

**FACT — `.target sm_89` PTX JITs and runs on an `sm_120` device. Two independent primary sources, HIGH.**
- PTX ISA 9.3 §11.1.2: *"generations of SM architectures follow an onion layer model, where each
  generation adds new features and retains all features of previous generations. **The onion layer
  model allows the PTX code generated for a given target to be run on later generation devices.**"*
- Blackwell Compatibility Guide §1.2: *"**PTX is forward-compatible. Meaning PTX is supported to run
  on any GPU with compute capability higher than the compute capability assumed for generation of
  that PTX.**"* … *"Application binaries that include PTX version of kernels should work as-is on the
  Blackwell GPUs."*
- The same section states the counter-case explicitly: *"PTX … with architecture conditional features
  using `sm_100a` or `compute_100a` … are **not** forward or backward compatible."* This is precisely
  why an FP4 family must be a *separate* module (§2.4).

### 2.2 Where the performance ceilings differ from Ada

| Axis | Ada `sm_89` (4050 dev box) | `sm_120` (5090 / PRO 6000) | Consequence for our constants |
|---|---|---|---|
| SMEM/SM, SMEM/block, warps/SM, blocks/SM, regs/SM | 100 / 99 KB, 48, 24, 64 K | **identical** | **No tile/stage/warp-tile shape re-derivation is possible or needed.** The 4050's shipped schedules are the feasible set. |
| SM count | 20 | 170 / 188 (**8.5–9.4×**) | Every "one wave", split-K threshold, persistent-CTA count, and raster/swizzle window is wrong by ~9×. **This is the #1 re-tune.** |
| L2 | 12 MB | 96 / 128 MB (**8–10.7×**) | Every NT-store / streaming decision keyed on "working set vs L2" flips. `velem`/`vhorner` NT thresholds must be re-derived, not scaled. |
| Memory BW | ~192 GB/s | 1792 GB/s (**9.3×**) | Bandwidth-bound families need ~9× more bytes in flight (Little's law) — more unrolling / more resident CTAs per SM, not a different kernel. |
| Tensor core | 4th gen | 5th gen, 4/SM (same count) | Per-SM fp16/bf16/int8/fp8 rates ≈ same shape; the win is SM count × clock. FP4/FP6 are *new* datatypes, not a speedup of existing ones. |
| INT32 lanes | 64 dedicated + 64 shared with FP32 | **128 unified FP32/INT32** | Address/index arithmetic (all our GEP chains) gets up to 2× issue headroom, but competes with FP32 for the same lanes. Net: ≥ Ada per clock; index-heavy SIMT kernels (paged-KV gather, scatter-add, strided col-reductions) benefit most. |
| INT4 tensor core | present | **removed** | Moot for us (§2.1), but a hard "never add" for any family whose floor is ≥ sm_90. |
| FP4 / FP6 tensor core | absent | present, `sm_120a`/`sm_120f` only | New family, non-forward-compatible module. §2.4. |

**DERIVED — machine balance, and why the 4050 is the right control.** FLOP:byte at the precision we
actually emit (fp16 mma with **fp32** accumulate):

| Part | fp16(f32-acc) TFLOPS | BW GB/s | FLOP:byte |
|---|---|---|---|
| RTX 4050 Laptop (20 SM @ ~2.37 GHz, Ada 512 FLOP/SM/clk at f32 acc) | ≈ 24 (derived, not a published figure) | ~192 (repo/plan figure) | **≈ 125** |
| **RTX 5090** | 209.5 (FACT) | 1792 (FACT) | **≈ 117** |
| **RTX PRO 6000 Workstation** | 503.8 (FACT) | 1792 (FACT) | **≈ 281** |
| H100 SXM (for scale) | ~990 (bf16 dense) | 3350 | ≈ 295 |

**The 5090 has essentially the same machine balance as the 4050 (117 vs ~125) — it is a 9× wider
version of the machine we already tune for.** The RTX PRO 6000 is 2.4× more compute-dense and sits in
H100 territory on balance. So: the 4050 is a legitimate same-class control **for the 5090**, and the
RTX PRO 6000 is a *different regime* wearing the same `sm_120` badge.

### 2.3 The FP32-accumulate trap (the most important derived finding)

**FACT (both whitepapers' spec tables, HIGH):** GeForce parts halve tensor throughput when the
accumulator is FP32; professional parts do not.

| | FP16 acc | FP32 acc | ratio |
|---|---|---|---|
| RTX 4090 | 330.3 | 165.2 | 2.0× |
| **RTX 5090** | 419 | **209.5** | **2.0×** |
| RTX 6000 Ada | 364 | 364 | 1.0× |
| **RTX PRO 6000 Blackwell** | 503.8 | **503.8** | **1.0×** |
| RTX A6000 (Ampere) | 154.8 | 154.8 | 1.0× |

Same for fp8: 5090 838 (f16 acc) vs 419 (f32 acc); PRO 6000 1007.6 either way.

**DERIVED consequences:**

1. **Wukong emits `…f32.f16.f16.f32` and `…f32.e4m3.e4m3.f32` everywhere — the halved path on every
   GeForce part.** This is *already* true on the 4050, so it is not a regression; it means our
   published `%-of-cuBLAS` on the 4050 is against a peer that is equally halved, which is fair. But it
   makes the roofline denominators device-class-dependent.
2. **A `%-of-peak` measured on RTX PRO 6000 over-predicts a 5090 by exactly 2× for fp16/fp8 GEMM.**
   The plan's framing — rent the PRO 6000 because *"it is the same ISA as an RTX 5090 — what
   enthusiasts actually own"* — is true for **codegen** and false for **performance**. Any number from
   that session must be labelled RTX PRO 6000 and never restated as "on a 5090".
3. **A 2× lever exists on GeForce Blackwell that does not exist on the PRO card: switch the
   accumulator to `.f16`.** PTX ISA 8.7 release notes: *"Extends `mma` instructions to support `.f16`
   type accumulator and shape `.m16n8k16` with FP8 types `.e4m3` and `.e5m2`."* This is exactly where
   the 838-vs-419 gap lives. See **UNRESOLVED U3** — whether the dense f16-accumulator fp8 `mma` is
   legal under `.target sm_89`, or needs a `sm_120` floor, is *not settled by the docs*, and it is a
   **$0 test on the existing 4050**: emit `.version 8.7` + `.target sm_89` +
   `mma.sync.aligned.m16n8k32.row.col.f16.e4m3.e4m3.f16` and see whether `cuModuleLoadData` accepts it.
   Numerics caveat: f16 accumulation over a K-loop breaks the `c·√K·ε` tolerance model — it needs its
   own error budget and its own fixture, and it should be opt-in, never the default.

### 2.4 Is a dedicated `sm_120` codegen family ever needed?

**DERIVED — for the current inventory: NO. The `sm_89`-floor + tuned-constants route is structurally
sufficient, and provably so**, because (a) every emitted instruction is sm_89-baseline, (b) forward
compatibility is a documented guarantee, and (c) the occupancy limits that determine schedule shape
are numerically identical to Ada. `sm_120` is the one rung of the ladder where "retag the header and
retune the constants" is the *complete* answer.

**A separate family becomes mandatory the moment we want any of:**

| Want | Required target | Forward compatible? | Structural cost |
|---|---|---|---|
| FP4 (`.e2m1`) / FP6 (`.e3m2`,`.e2m3`) `mma` | `sm_120a` (or `sm_120f`, PTX ≥ 8.8) | **NO** | separate PTX module, emitted only when probe says CC 12.x |
| Block-scaled MMA (`.kind::mxf8f6f4`, `.kind::mxf4`, `.kind::mxf4nvf4`, `.block_scale`, `.scale_vec_size`) | `sm_120a`/`sm_121a` | **NO** | ditto + scale-factor layout + `cvt…rs` rounding |
| `ldmatrix.m16n16/.m8n16`, `stmatrix.m16n8` | `sm_120a` | **NO** | ditto (marginal payoff) |
| fp8 mma with `.f16` accumulator | sm_89? or sm_120 — **U3** | probably yes | `.version` bump to 8.7 + tolerance rework |
| TMA / clusters / DSMEM | `sm_90` baseline | yes | this would be a **shared sm_90+ family**, not sm_120-specific — H100 work that `sm_120` inherits for free |

**Note the asymmetry that matters for the emitter's design:** today every generator writes a fixed
`".version 7.8\n.target sm_89\n"` header (67 sites). The `GpuTarget` refactor should treat the header
as **(`.version` floor, `.target` floor)** *per family*, not a single global string — because
`sm_120a` families need a *higher* `.version` AND a *non-forward-compatible* `.target`, and a driver
older than the family's `.version` floor must decline the family (a loud capability skip), never emit
PTX the driver cannot parse.

**DERIVED — what FP4/FP6 would actually buy.** Two distinct designs, very different value:

- *Weight-only decode (what our int4 W4A16 already does).* `lop3`-unpack 4-bit weights straight into
  `f16x2` and feed the **fp16** tensor core. FP4 tensor cores add **nothing** here — the kernel is
  weight-bandwidth- and decode-bound, and the mma is already fp16. Our existing int4 family is
  therefore *complete* on `sm_120` and needs no FP4 work at all. Do not confuse "the GPU has FP4" with
  "our int4 kernel gets faster".
- *Full FP4 mma (W4A4 / NVFP4 / MXFP4).* Both operands in `.e2m1` with per-block E4M3/E8M0 scales via
  `.block_scale`. On a 5090 that is 1676 TFLOPS vs 209.5 for our current fp16-f32acc path — an **8×
  tensor-throughput ceiling**, or 4× vs an f16-accumulate fp8 path. It only pays in *compute-bound*
  regimes (prefill, batched serving); batch-1 decode is bandwidth-bound and already captured by
  weight-only int4. Cost: a new numerics surface (block scales, calibration, an oracle that is not
  circular), a non-forward-compatible module, `.version` 8.7+, and no fair library peer on consumer
  parts except TensorRT-LLM / Marlin-class FP4 kernels. **Recommendation: defer until after H100, and
  scope it as a serving/prefill feature, not a GEMM-family refresh.**

### 2.5 One latent bug this research surfaced (repo-side, free to fix)

`crates/wukong_codegen_gpu/src/cubin.rs:88` — `cache_path(ptx, tag)` hashes **only the PTX text**, with
the driver version as `tag`. The doc comment reasons: *"the arch lives inside the PTX text, so it is
covered by the hash."* That is true of the **virtual** arch and false of the **device SASS**. Identical
`.target sm_89` PTX JIT'd on an `sm_89` device and on an `sm_120` device produces two different cubins
at **the same cache path**. Today this is safe-but-wasteful (an incompatible cubin fails
`cuModuleLoad` and falls back to the PTX JIT), but it becomes live the moment a cache directory is
shared across a heterogeneous fleet or a persisted Modal volume. **Once `GpuTarget` exists, the cubin
cache key must include the device compute capability (and ideally the device name).** Cheap, local,
$0, and exactly the kind of thing that would otherwise be discovered at $3/hr.

## 3. UNRESOLVED (stated honestly)

- **U1 — SMEM/SM on CC 12.0: 100 KB or 128 KB?** Blackwell Tuning Guide says 128 KB; CUDA PG Table 31
  says 100 KB; PTX ISA §5.1.7 says 100 KB for `sm_120a`; the legal carveout list ends at 100. Resolved
  *in favour of 100 KB* with high confidence (128 KB = unified L1+SMEM), but the tuning guide's
  sentence is wrong or misleading as written. **Settle it in the probe**, one attribute query.
- **U2 — is `mma…s4/u4` rejected on `sm_120`?** CUDA PG Table 33 says INT4 tensor-core acceleration is
  absent from CC 9.0/10.x/11.0/12.x. The PTX ISA's `mma` Target ISA Notes give only a *lower* bound
  ("`.u4/.s4` … requires sm_80 or higher") with no upper bound, which the onion-layer model would read
  as "still legal". Whether `ptxas` errors, or silently emulates at low rate, on `sm_90`+ is **not
  documented**. Moot for Wukong today (we emit no `s4` mma) — but it is a hard constraint on any
  future native-int4 family, and it is the one place where the onion-layer promise appears to leak.
- **U3 — fp8 `mma` with `.f16` accumulator: what is the target floor?** PTX 8.7 added the spelling; the
  *dense* `mma` notes say only "`.e4m3`/`.e5m2` … requires sm_89 or higher", while the *sparse* notes
  say "shape `.m16n8k32` and `.f16` dtype/ctype with `.e4m3`/`.e5m2` … **requires `sm_120`**". Ada
  hardware clearly *has* the 2× f16-accumulate fp8 rate (4090: 660.6 vs 330.3), which argues sm_89 is
  fine. **$0 local experiment on the 4050 settles it** and is worth doing in Wave 0.
- **U4 — thread-block clusters on `sm_120`.** CUDA PG Table 29 marks Thread Block Cluster, Distributed
  Shared Memory and TMA as "Yes" for 12.x. The maximum *portable* cluster size on CC 12.0 is not
  established here. We emit no cluster code, so this is future-work information only.
- **U6 — which RTX PRO 6000 edition does Modal rent?** Workstation, Max-Q and Server editions share the
  GB202 die and 1792 GB/s but differ in clocks/TDP (Max-Q is ~13% lower on every tensor row: 438.9 vs
  503.8 TFLOPS). A rented "RTX PRO 6000" whose edition is unrecorded makes the round unreproducible.
  **Record `nvidia-smi -q` (name, clocks, power cap) in every round log** and treat the edition as part
  of the instrument.

## 4. PREDICTIONS — the 4-point checklist for a future ~$3/hr RTX PRO 6000 session

Written *before* any silicon. A failed prediction is the point.

**Point 1 — LOAD (budget: 10 min, ~$0.50). Predicted: clean pass.**
- Every one of the 67 `.target sm_89` PTX modules JIT-compiles and `cuModuleLoadData`s on CC 12.0
  without a single source change. **P ≈ 0.97.** Failure modes ranked: (a) a generator that emits a
  non-ASCII character only on a path the 4050 never took (the ASCII gate should already forbid this);
  (b) an `.extern` / driver-API assumption; (c) nothing else — there is no arch-specific instruction to
  trip on.
- **Cubin cache: 100% miss** (§2.5 — key omits device CC). Cold JIT per module ~0.7–1.5 ms, same order
  as the 4050's measured 0.76 ms cold / 0.16 ms warm. Do **not** interpret the miss as a bug in the
  first five minutes; it is expected and is fixed for free beforehand.
- Deliverable: a `nvidia-smi -q` + `cuDeviceGetAttribute` dump of *every* attribute the future
  `GpuTarget` will query, committed as a raw artifact. This is the "never pay twice for the same fact"
  purchase — it also settles U1 and U4 permanently.

**Point 2 — CORRECTNESS (budget: 20 min, ~$1). Predicted: all oracle-gated fixtures pass.**
- Integer families (int8 GEMM, int8 dequant, argmax) — **bit-identical to the 4050**, because integer
  `mma` is exact and the accumulation order is fixed by the same PTX. **P ≈ 0.95.**
- Floating families with a fixed accumulation order (fp16/bf16/fp8 GEMM at the same tile shape, no
  split-K, no atomics) — **also predicted bit-identical to the 4050**, since identical PTX ⇒ identical
  mma sequence ⇒ identical rounding. **P ≈ 0.8**; the 20% is fma-contraction / reassociation freedom in
  the driver's SASS scheduler for the *non*-mma epilogue arithmetic.
- Anything using atomics, split-K, or a CTA-count-dependent reduction order — **not** bit-identical,
  and must be gated on the `c·√K·ε` tolerance. Any fixture that silently assumed bit-exactness because
  it only ever ran on one device will be exposed here. **That exposure is a deliverable, not a bug.**
- Predicted failures: 0 correctness failures, 1–3 *fixtures* that need their gate relaxed from
  bit-exact to tolerance.

**Point 3 — WHICH RE-TUNES MATTER, ranked by predicted effect size.**
1. **Grid / persistent-CTA / raster constants (9.4× SM count).** Everything keyed to 20 SMs is wrong.
   Predicted effect: **2–5×** on mid-size GEMM and on every `@parallel` region, purely from filling the
   machine. This one re-tune is expected to dominate the entire session.
2. **L2-residency thresholds (10.7× L2).** NT-store / streaming decisions keyed on "total working-set
   bytes vs L3/L2" (the `velem`/`vhorner` rule) will choose NT stores for shapes that now fit in 128 MB
   of L2. Predicted effect: **1.2–2×** on the streaming-elementwise family, and possibly a *regression*
   if left unchanged — the most likely place for an embarrassing loss.
3. **Split-K / regime-dispatch thresholds.** The small/mid/large GEMM boundaries were fitted at
   FLOP:byte ≈ 125; the PRO card sits at 281. Predicted: the "small" regime widens substantially.
4. **Autotuner cache: re-run from scratch, persist under a device-keyed name.** Never reuse the 4050's.
   The *search space* is unchanged (§2.2 — identical SMEM/warp/reg limits), so this should be a
   **confirmation of a derived 6-point shortlist, not a blind 40-point sweep.**
5. **Bandwidth-bound unrolling.** Little's law: 1792 GB/s × ~500 ns ≈ **900 KB in flight** vs the 4050's
   ~87 KB. Predicted: `saxpy` lands at **85–93%** of device peak on first run (vs the 4050's measured
   95.7%), and recovering the last few points needs more bytes in flight per thread (deeper unroll /
   wider vector loads), not a new kernel. **This is the most falsifiable prediction in the dossier.**

**Point 4 — WHAT TO MEASURE, with the 4050 as the same-class control.**
- **The primary metric is per-SM-per-clock throughput**, not absolute GFLOP/s:
  `T_norm = achieved_FLOPs / (SMs × boost_clock)`. If the `sm_89` code is generation-neutral,
  `T_norm(PRO 6000) / T_norm(4050)` should be **≈ 1.0** for every fp16/bf16/int8/fp8 family.
  - `> 1.15` ⇒ the 5th-gen tensor core gives a per-SM gain we did not expect — investigate, and check
    it is not the FP32-accumulate asymmetry (§2.3) doing the work.
  - `< 0.85` ⇒ our tiling under-fills the wider machine — that is re-tune #1, not a hardware fact.
- **Report the RTX PRO 6000 and any 5090 extrapolation separately, and halve the fp16/fp8 f32-accum
  roofline before speaking about a 5090 at all.** Better: state both denominators explicitly in the
  round log so the retraction can never be needed.
- **Bandwidth families**: report `% of device peak` (1792 GB/s), which *is* directly comparable to the
  4050's 95.7% figure because both are ratios against their own peak.
- **Adjacent same-run A/B only**, best-of-N minima, control column included — the Windows-scheduler
  lesson transfers: on a rented Linux box the equivalent confound is **clock ramp / power cap**, so
  interleave A and B within one process and record `nvidia-smi --query-gpu=clocks.sm,power.draw` before
  and after, exactly as the laptop's power state is checked before and after each round.
- **Do not publish a `%-of-cuBLAS` from this session as a `sm_120` headline** unless cuBLAS was built
  and run in the same process on the same card in the same round. The plan's own rule.
